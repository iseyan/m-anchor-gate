# 実証1号：保存した区別の再開後利用 v0.1

原因候補A/Bを保持したまま対応Bを選び、別プロセスで正式な保存状態を読み、判断へ使う固定入力の実行例。

主場面の判定文は次のままである。

> a_Bは選択済み／原因A・Bは未決

仕様原稿は `specs/` に収録した。保証範囲・場面仕様の英日原稿と、Python v0.1の検査器・既存9テストは変更していない。実証はBundle 1.0とは別版である。

## 実行

展開先のこのフォルダーで実行する。実行系はPython標準ライブラリのみを使う。APIキーは不要。

```bash
python run_demo.py --output-dir results/new-run
python -m unittest discover -v
```

出力先には未作成のフォルダーを指定する。既存の結果を上書きしない。WindowsでPython 3.13を選ぶ場合は `python` を `py -3.13` に置き換えられる。Python 3.10以降を想定し、今回の実行確認はLinux / Python 3.12.14で行った。Windows / 3.13での実行結果は含まない。

## 構成

| ファイル | 役割 |
| --- | --- |
| `m_anchor_minimal.py` | Bundleに含まれた77行の検査器を無変更で使用 |
| `demo1.py` | 固定した証拠解釈、検査を通る更新、SQLite保存、読取値に基づく判断 |
| `writer.py` | 固定提案を再生し、対応と要約を保存して正常終了 |
| `reader.py` | ケースIDと保存先だけを受け取る別プロセス |
| `run_demo.py` | 書込終了後に読取プロセスを起動し、その外側で期待値を照合 |
| `schemas/` | 状態・再開判断記録のJSON Schema |
| `results/observed-2026-09-29/` | 今回のデータベース、記録、プロセスの起動・終了順、判定、環境、ソースハッシュ |

状態版0から1への更新では、検査済み状態・対応記録・受理監査を一つのSQLiteトランザクションに入れる。要約の保存、拒否記録の保存、再開判断の保存は状態版を進めない。過去の状態は置き換えず、各版を保持する。

証拠登録表は検査側に固定する。`e_B` の解釈は `{h_B}`、証拠なしの解釈はΩである。提案側から互換候補集合や解釈規則を指定できない。証拠の真偽は審査しない。

再開側は正式な状態、状態が参照する対応記録、要約を読む。判断関数の入力は読んだKと対応だけである。状態版、入力、適用規則、結果、プロセス識別子、状態と対応のハッシュを同じ判断記録に保存する。ハッシュは記録同士の対応確認に使い、改ざん防止を保証しない。

## 確認範囲

保存、根拠なし更新の拒否、別プロセス再開後の利用、証拠あり対照の四条件を確認する。主場面と対照で同じ再開処理を用いる。要約の差し替え、読取状態の欠落、対応値の変更、監査保存失敗時のロールバックなども追加6テストで確認する。

これは固定入力と明示した決定規則による実証である。LLMの読解・推論・改善効果を測ったものではない。Bは固定入力で、外部フォームへの提出や実世界の操作は行わない。モデル内部、証拠解釈の真偽、権限制御、並行更新、障害復旧、特権による直接書換えへの耐性は対象外。

JSON Schemaは記録形式の定義であり、実行時の汎用入力検査器ではない。今回のスキーマ点検はJSON構文と出力記録の最上位項目の一致までで、外部のJSON Schema検証器は使っていない。集合保存条件は既存検査器、場面の受入条件は `run_demo.py` で検査する。
