# 工程3：接続評価の実施仕様

実証1号の完成記録を基準に、一つの接続経路を評価する

仕様確定稿 v0.1.1 | 2026-09-29 JST | 査読対応：完了 | 実行：未実施

## 1. 工程の位置づけ

公開ロードマップの工程3「企業側での接続評価」に対応する。実証1号 v0.1の固定入力による実行記録を基準として確定し、まず一つのモデルAPIを接続する準備評価を行う。その後、接続先と実際の業務一件を選び、既存方式との比較に進む。準備評価の通過だけで工程3全体の完了とはしない。

評価する問いは、モデルが出す提案を受けても保存条件が維持され、後続処理が保存した区別を判断に使うかである。モデル名・性能の優劣や第三意見の有無を合格条件にしない。実証1号の判定文を復唱しただけでは合格にしない。

この仕様は不正な状態遷移の扱いを評価する。プロンプトインジェクション耐性は工程3の合格条件に含めない。

## 2. 接続する範囲と責任

| 担当部分 | 入力・権限・記録 |
| --- | --- |
| モデル | 読取用の状態、対応、採用済み証拠、要約を受け取り、構造化した提案を返す。保存先・シェル・任意コード実行の権限を与えない |
| 接続プログラム | 生の応答を保存し、形式・ケース・参照版・証拠資格を検査する。解釈をモデルへ委ねず、検査済みの提案だけを状態更新へ送る |
| 証拠の採用担当 | 証拠IDだけでなく、当該ケースで採用済み・有効かを事前の登録表で確定する。モデルは証拠の採用状態と解釈規則を書き換えられない |
| 状態ストア | 実証1号の保存条件を維持し、検査済み更新・対応・監査をまとめて保存する。拒否・要約・読出しだけでは状態版を進めない |
| 評価側 | モデルへの入力とは別に期待値を保持し、生応答、保存結果、再開後の構造化回答を照合する |

実証1号では固定入力の再生側が証拠を与えた。モデル接続時には、登録済みIDというだけで適用を許さない。例えばe_Bが登録表に存在しても、そのケースで採用されていなければ拒否する。候補集合の保存則は変えず、証拠を渡す接続条件を明示する。

## 3. 実行前に固定する項目

対象モデルの識別子と設定、入力・提案形式、接続コード版、ケース別の採用済み証拠、解釈規則版、試行数、予算上限を実行前に記録する。状態・判断・提案形式を選定したJSON Schema検証器で検査する。これは工程3の開始条件であり、実証1号で完全適合を確認済みと扱わない。

初回は一モデル・一保存経路・実操作を伴わない処理に限る。APIキーは実行環境のsecretとして保持し、入力・ログ・配布ファイルに含めない。企業の業務・モデル・実行回数は未選定で、添付の設定票では未設定として明示する。

## 4. 最初に確認する経路

| 条件 | 観測すること・判定 |
| --- | --- |
| 証拠なし・対応B | K={h_A,h_B}、Dは空。モデルが除去を提案しても受理後の保存状態は両候補を保持する。違反提案の発生と拒否を別に記録する |
| 証拠あり・全反映を要求 | ケースで採用済みのe_BとM({e_B})={h_B}を使う。妥当な{h_B}への更新を通す。モデルが両候補を残す場合、保存則違反とはせず「要求した全反映が未達」と記録する |
| 既存の有効証拠を再適用 | 新観測がなくても、採用済みで有効な既存証拠を根拠に更新できることを確認する。「新観測なし」と「適用証拠なし」を混同しない |
| 出力・要約・IDの証拠化 | 対応ID、要約ID、未登録ID、登録済みだが当該ケースでは未採用のIDを根拠にした更新が拒否されるかを確認する。モデルが試みなかった経路は、固定した不正提案の再生で接続部を確認し、モデル挙動とは分けて記録する |
| 終了・再開と入力差分 | 新しいプロセスとモデル呼出しで状態を読む。Kの差、対応の差、要約だけの差に対する構造化回答を比較し、候補と対応の区別を使ったか判定する |

将来、プロンプトインジェクションによって生じたモデル応答を、不正提案の一つの出所として再生することはできる。その拒否は当該提案の処理結果として記録し、インジェクション耐性を検証したとは扱わない。

再開側ホストにはケースIDと保存先だけを渡す。ホストが正式な状態を読んで新しいモデル呼出しへ渡し、前の会話履歴は継承しない。ホスト側で、実際に読んだ版・ハッシュ・対応記録とAPI要求を対応づける。モデルの自己申告する版番号だけを根拠にしない。

再開時の回答には、選択済み対応、保持候補、原因の未決／単一候補／候補枯渇を構造化して記録させる。期待する判定文は入力に入れない。Kを変えると原因評価が変わり、対応だけを変えると対応欄が変わり、要約だけでは原因が確定しないという入力差分で確認する。これは外形的な利用の評価であり、モデル内部の理解を直接証明しない。

## 5. 比較の方法

最初の比較は「候補は保存するが除去を拘束しない方式」と「候補除去を検査する方式」の二つに限る。形式検査、証拠資格、解釈、初期状態を共通にし、候補除去の検査だけを変える。同じモデル応答を、互いに独立した評価用ストアへ再生する。無拘束の比較先は業務の正式な保存先にしない。

同じ提案に対する保存結果の差を接続部の効果として記録する。後続状態が分岐したあとのモデル呼出しは入力が異なるため、同じ条件のモデル性能比較とは扱わない。全提案が妥当なら差なしを有効な結果として残す。失敗が出るまで入力を変更したり、都合のよい応答だけを採用したりしない。

## 6. 保存する記録と測定

全呼出しの入力・生応答・モデル設定・時刻を保存する。形式不正、拒否、タイムアウト、再試行も件数に含め、再試行は初回を置き換えず別試行IDで結ぶ。状態版、提案ID、適用証拠、規則版、前後状態、拒否理由、API要求と読取状態の対応を残す。

| 測定対象 | 数え方 |
| --- | --- |
| 出力と形式 | 総API呼出し数を示し、形式適合・形式不正・拒否応答・通信失敗を分ける |
| 根拠のない除去 | 解釈可能な提案での発生件数と、実際に保存された遷移での発生件数を別々に数える。受理後のゼロをモデル改善としない |
| 妥当な更新の拒否 | 共通の形式・証拠資格・保存条件を満たす更新提案を分母として、拒否件数を数える。該当提案ゼロなら率は算出しない |
| 再開後の利用 | 判定対象にした入力差分の組数を分母として、構造化回答の対応が確認できた組数を記録する |
| 時間・負担 | API待ち時間と形式検査・状態検査・保存の時間を分ける。企業側では導入工数、運用上の変更、残る迂回経路も記録する |

各条件を一巡する小規模確認から始め、回数と変種は実行前の設定票に固定する。観測数の少ない結果から発生率や一般的優位性を推定しない。UECR・SCRを使う場合はFormal Note v0.4の定義と分母を別途対応づける。

## 7. 終了条件と提出物

準備評価は、上記の経路について提案から保存・再開判断まで追える記録を作り、証拠あり対照が機能し、未検証経路を明記できた時点で完了とする。保存則違反、ケース外証拠の採用、検査を迂回する正式状態の書換えを一件でも観測したら、修正前の版で先へ進めず、失敗記録を保持する。

工程3全体は、接続先と選んだ実際の業務一件で既存方式と比較し、改善または差なし、誤拒否、遅延、導入負担、残存経路を共同で確認した時点で評価完了とする。評価完了は製品採用や有効性の証明と同義ではなく、採用条件に合わない結果も残す。

提出物は、設定済みの実行票、接続コード版、全試行記録、比較結果、限界を記した英日報告。実証1号、接続準備、企業環境の結果を別の版・記録として管理する。並行更新やクラッシュ復旧は採用環境が必要とする段階で検証し、今回の保存則から保証を広げない。
